# Affiliate de-duplication manifest — 2026-09-22

**954 rows deactivated. None deleted.** Undo:
`scripts/studio/restore-affiliate-dedupe-2026-09-22.sql`.

## Root cause

`public.affiliates` had unique indexes on `id` and `referral_code` but
**none on `user_id`**, and `ensureReferralCode` in the client INSERTed a
new row whenever it could not find an active one. Nothing stopped a burst
of concurrent callers each minting their own. Hence 344 rows on
2026-06-12, 375 on 06-13 and 207 on 09-06 for a single account.

Fixed at source in the same batch:

- the client no longer inserts; it calls `ensure_my_referral_code()`
- `affiliates_one_active_per_user`, a partial unique index on `user_id`
  where the row is active, makes a second active row impossible

## No circulating link was broken

`process_referral` used to filter its lookup on
`COALESCE(is_active,true) = true`, so deactivating a row would have made
that code stop resolving. It now resolves a code **regardless of
`is_active`**, preferring active rows on a tie. `is_active` governs which
code is handed out, never whether an old one still works.

Verified after the change: `S2G-ZUKZ4HV1` (now inactive) still resolves to
davison.taljaard, and the 8-hex `8A2E07FD` still resolves to
chariwellnesspro.

referrals. That leaves 3 active rows for davison.taljaard, which makes a
