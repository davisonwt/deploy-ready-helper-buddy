## P0 — money can go wrong, or a security hole

### P0-1. The weekly payout function sends real money if its request body is unreadable
**What.** `payout-earnings` decides whether a call is a "preview only" dry run
by reading `dry_run: true` from the request body. If the body cannot be
parsed as JSON for any reason, it is silently treated as empty, and an empty
body means a real run. Today two calls that were meant as dry runs were
handled as real runs because a pasted key added a line break to the request.
One of them sent 2 USDC.
**How I know.** `supabase/functions/payout-earnings/index.ts:263-264`
(`req.json().catch(() => ({}))`, then `dry_run === true`). Live proof: the
responses at 10:2x UTC today had the real-run shape (`paid`, `skipped`,
`outcomes`) and the second one produced signature `vwHDdF…`.
**Status.** Confirmed live.
**Who it hurts.** S2G money.
**Fix size.** Small. Refuse a body that is not valid JSON, and require an
explicit `confirm: "send"` (or similar) for a real run so the default is the
safe one.

### P0-2. A devnet test marked a real earning of Amber's as paid
**What.** The devnet test run today settled `product_bestowals` row
`02c6b716…` (Amber's real $2.00 sale) with test USDC. The database says she
was paid. She was not. Until reverted, the weekly run will never pay her for

**Status.** Confirmed live.
**Who it hurts.** A member (Amber).
**Fix size.** Small. The revert SQL was printed in chat today (returns the
bestowal to `pending`, marks the devnet payouts row `failed`). Run it, then
check `904058fc…`.

### P0-4. Profiles: privacy enforced since June; the app's public reads were starved. FIXED 2026-09-05
**Correction (2026-09-05, from the live policy list).** The 2026-04-23
"anyone can read everything" policy cited in the first version of this
entry was replaced on 2026-06-18 (migration `20260618154229`). Live, a
member can read only their own row, and admin/gosat can read all
(`profiles_select_self_or_admin` via `can_access_user_data`). So no member
could read another member's email, phone, birthday, coordinates or payout
address. The real defect was the opposite: about 65 direct reads and 19
embedded joins that show other members' names and avatars were silently
getting nothing, and the `profiles_public` view meant to serve them had
`security_invoker = true`, so it inherited the same lock.
**Fix.** Migration `20260905160000_profiles_public_view.sql` recreates
`profiles_public` with `security_invoker = false` exposing only the
owner-approved public columns (plus birthday month/day and social URLs
gated by the member's own show flags), readable by anon and authenticated.
62 direct reads and 17 join sites moved to it; joins whose source table has
no foreign key to profiles (products, bestowals, radio_djs, sowers) became
two-step fetches. Own-row and admin screens still read `profiles`.
**Status.** Live proof: as a non-admin member, `profiles_public` returned
70 rows, `profiles` returned 1. Browser rendering: unverified (no test
accounts exist; see the gated Playwright spec).
**Fix size.** Done.

### P0-5. Orchard money is not held apart, and there is no refund path
**What.** The spec (section 10) says orchard pockets are all-or-nothing:
funds sit in dedicated Launch and Uplift wallets, nothing is released until
fully funded, and the money is a liability, not S2G's. In the code an
orchard bestowal is paid into the ordinary hot wallet or PayPal account like
any sale, and the only thing that happens when an orchard fills is that a
chat room is created. The two orchard wallet addresses from the spec appear
nowhere in the application code. There is no cancel or refund path for an
orchard that never funds.
**How I know.** Completion trigger `auto_generate_premium_room` in
`supabase/migrations/20251001104708_….sql:60-100` (creates a chat room and a
notification, nothing about money). Grep for the spec's wallet addresses and
for `LAUNCH_ORCHARD` / `UPLIFT_ORCHARD` in `src` and `supabase/functions`:
no hits. Grep for `refund` in functions: only payment-provider webhook
handling, no orchard path. `create-orchard-bestowal-order` routes to the
same providers as everything else.
**Status.** Confirmed in code.
**Who it hurts.** Members' money (gifts to an orchard that never funds are
mixed with operating float and cannot be returned), and S2G's books.
**Fix size.** Large.

## P1 — a member-facing flow that is broken or misleading

**How I know.** `src/components/admin/EnhancedAnalyticsDashboard.jsx:155-171`.
**Status.** Confirmed in code.
**Who it hurts.** S2G money decisions; cosmetic in the best case.

**What.** Three admin tiles are labelled Total Revenue. `BasicAnalytics`

## P2 — works but should be better

### P2-1. Order-creation functions have no rate limit
`create-solana-bestowal-order`, `create-orchard-bestowal-order`,
`create-gift-bestowal-order`, `create-content-purchase-order`,
`create-paypal-order`, `create-booking-paypal-order`, `purchase-music-track`
create database rows and provider orders with no `checkRateLimit` call. A

Security/abuse. Small each.

### P2-2. The spec contradicts itself on the Solana payout minimum
Section 8 says "USDC on Solana: none, pay immediately, any amount". Section

the fee deducted) is not built: `request-earnings-payout/index.ts:117-125`
only tells PayPal recipients to wait. Confirmed in code. Members on PayPal
with small balances. Small (doc) plus medium (release valve).

(`send-xrp-payout`, `xrp-quote`), Binance (`refresh-binance-wallet-balance`

## Area notes

### 1. Money math
Every live path agrees with the spec's "15% on top, whisperer out of the
base, grower pays the processor fee":
- Client: `src/lib/pricing/platformFee.ts`; server: `supabase/functions/_shared/platformFee.ts`; the two are pinned equal by `platform-fee-drift.test.ts` (12 tests, passing).
- Basket sales: `create-basket-bestowal-order` stamps `unit_price`, `line_total`, `fee_inclusive: true`; `finalize_basket_order` (migration `20260904180000`) splits base-on-top and takes the whisperer share from the base. Legacy lines back out `/1.15`.
- Content purchases, gifts, bookings: `priceBreakdown()` server-side; processor fee via `computeBuyerFee` on top.
- Orchards: `pocket_price` is the one deliberate fee-inclusive exception; `distribution.ts` backs the fee out. `CreateOrchardPage.jsx:535-552` and `SeedSubmissionPage.jsx:241-268` store `buyerTotal(base)` as `pocket_price`, which is the intended model for orchards.
- Product writers store the base: `UploadForm.tsx:176-186`, `EditForm.tsx:105`; Playwright tests 3 and 4 prove it (type 2.00, saves 2, not 2.30).
- Double-15% recurrence risk: any new writer to `products.price` or any reader that calls `priceBreakdown()` on an already-grossed number. Nothing found today. The `bestowals` table's `s2g_fee` is derived as a residual in `sower_earnings_v` because the table never stored it, so old orchard rows depend on `distribution_data` being right.
- Amber's $1.95 rows from before the fix were corrected on 2026-09-04 (SESSION-STATE ~3110); one more `credited_to_balance` row (`2d195090`) is still open in SESSION-STATE item 1.

### 2. Payout pipeline
- Double-pay protection: `markCoveredRowsProcessing` is a compare-and-swap; a concurrent run that loses the race reverts to pending and sends nothing. Good.
- Partial failure: per-recipient try/catch; a send that succeeds but whose DB update fails is logged "NEEDS A HUMAN" and left `processing` so it is never retried automatically. Good, but nothing surfaces that log to a gosat except the function logs.
- Cooling-off 48h after a payout-address change: enforced in both `payout-earnings` and `request-earnings-payout`.
- Caps: $50 per transaction, $200 per day on the Solana leg (env-overridable).
- Dry run flag: not reliable, see P0-1.
- Threshold: $20 on both rails on the automatic run; $1 on request for Solana. See P2-2.
- Heavy SDKs: only `send-xrp-payout` (see P2-3).
